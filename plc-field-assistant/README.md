# ПЛК Помощник

Единое приложение для обучения и полевой работы с ПЛК: 2D-тренажёр с
ST-подобным языком и заданиями по уровням (перенесён из корневого
`index.html`) плюс полный набор офлайн-инструментов наладчика — журнал
неисправностей, таблица I/O, список замечаний, паспорт оборудования,
реестр версий проектов, инженерные калькуляторы, мастер диагностики
неисправностей и офлайн-справочник по пяти томам курса. Все данные — в
IndexedDB на устройстве, интернет не нужен.

Реализованы все три этапа из ТЗ: модули 1–8 плюс статистика. Сверху —
объединение с тренажёром и три способа установки: обычный сайт/PWA,
урезанная PWA для телефона и установщик под Windows (Electron, `.exe`).

## Три сборки из одной кодовой базы

| Команда | Что получается | Для чего |
|---|---|---|
| `npm run build` | `dist/` — полная версия, включая тренажёр | Обычный сайт / PWA на десктопе |
| `npm run build:phone` | `dist-phone/` — только Журнал, Калькуляторы, Справочник | Урезанная PWA для телефона («Добавить на экран Домой» в Safari/Chrome) |
| `npm run dist:win` | `release/*.exe` — NSIS-установщик Windows | Полноценное приложение, ставится как обычная программа |

Переключение набора вкладок и путей идёт через режим сборки Vite
(`--mode phone` / `--mode electron`) и `import.meta.env.VITE_APP_TARGET`
(см. `src/App.tsx`) — компонентный код один и тот же, различается только
то, какие вкладки регистрируются и как резолвятся ассеты (абсолютные пути
`/…` для сайта/PWA, относительные `./…` для Electron, который грузит
`index.html` через `file://`).

## Тренажёр (вкладка «Тренажёр»)

`public/trainer/index.html` — копия корневого `index.html` (2D-канвас,
интерпретатор ST, задания по уровням, песочница). Он самодостаточный
(без внешних зависимостей), поэтому просто встроен как статический ассет
и открывается в `<iframe>` (`src/modules/trainer/TrainerPage.tsx`) на
относительном пути `trainer/index.html` — это обязательно, абсолютный
путь `/trainer/index.html` сломается в Electron-сборке под `file://`.
`localStorage` тренажёра (`plcTrainerCompleted`, `plcSandboxScene`,
`plcSandboxCode`) живёт в том же origin, что и остальное приложение,
но с непересекающимися ключами — конфликтов с `pfa-*` ключами помощника
нет.

**Если меняешь корневой `index.html`** (тренажёр) — не забудь
скопировать изменения в `plc-field-assistant/public/trainer/index.html`
(`cp index.html plc-field-assistant/public/trainer/index.html` из корня
репозитория), иначе вкладка «Тренажёр» останется на старой версии.

Конвейеры стыкуются по-настоящему: `railExitPoint`/`railEntryPoint`/
`resolveExit` в `index.html` находят соседний конвейер (или дивертор),
чей вход геометрически совпадает с твоим выходом и смотрит в ту же
сторону, и передают коробку на него — вместо старой проверки только
близости к воротам. У конвейера теперь очередь коробок (`state.boxes`,
не одна `boxX`), так что многосекционная линия несёт продукт непрерывно.
Одиночный конвейер без входа сверху по-прежнему сам зацикливает одну
деталь — для обратной совместимости с уже существующими заданиями.
**Дивертор** (`DEVICE_DEFS.diverter`) — новый рельсовый прибор: стоит
между конвейерами и по тегу `_Divert` уводит коробку либо прямо, либо
на 90° в сторону.

## Связь с CODESYS (OPC UA)

Кнопка «⚙ CODESYS» на вкладке «Тренажёр» (видна только в
Electron-сборке — браузер физически не может открыть OPC UA соединение)
открывает панель `src/modules/codesys/CodesysPanel.tsx`: адрес OPC UA
сервера CODESYS, таблица тегов сцены с полем NodeId у каждого и кнопка
«Запустить синхронизацию». При старте синхронизации приложение
останавливает встроенный ST-интерпретатор тренажёра (`pauseScan` —
обёртка над уже существующим `stopScan()`) — дальше тегами управляет
реальный CODESYS, а сцена (конвейеры, датчики, физика) продолжает жить
своей жизнью независимо, как и раньше (`stepPhysics`/`draw` никогда не
зависели от scan-таймера).

Схема моста:

- **`electron/opcuaBridge.js`** — тонкая обёртка над `node-opcua-client`
  (единственная активная сессия), реально живёт только в main-процессе
  Electron (raw TCP недоступен из renderer/iframe).
- **`electron/preload.cjs`** — `contextBridge` прокидывает пять операций
  (`connect/disconnect/status/read/write`) в `window.electronAPI.codesys`
  у рендерера — и ничего больше (никакого `fs`/`net`/произвольных IPC).
- **Тренажёр ↔ React** — `index.html` раз в 150мс шлёт снимок тегов
  (`postMessage({source:'pfa-codesys-snapshot', ...})`) в родительское
  окно; `useTrainerBridge.ts` его ловит. **postMessage, а не прямой
  `iframe.contentWindow`** — под Electron внешняя страница и трейнер
  это два разных `file://` документа (разное происхождение), прямой
  доступ не гарантирован политикой same-origin.
- **`CodesysPanel.tsx`** — раз в 250мс для тегов с проставленным NodeId:
  OUT-теги (CODESYS управляет прибором — мотор, лампа, ворота) читает из
  OPC UA и пишет в сцену; IN-теги (сцена сообщает состояние — датчик,
  кнопка) читает из сцены и пишет в OPC UA. Синк-тик держит снимок/конфиг
  в `useRef`, а не читает их из замыкания напрямую — иначе `setInterval`
  захватывает их значения на момент старта синхронизации и не видит
  ничего, что пришло позже (классический баг устаревшего замыкания,
  отловлен и исправлен при разработке — см. git history).

Проверено сквозным тестом против собственного mock OPC UA сервера
(`node-opcua-server`, не входит в зависимости приложения — только для
разработки): подключение к несуществующему серверу не роняет приложение
и показывает ошибку; при подключении к рабочему серверу OUT-тег реально
меняется от внешнего источника и это видно на сцене, а IN-тег с сцены
реально долетает до сервера. Против настоящего CODESYS не тестировалось
(нет установленного CODESYS в песочнице разработки) — нужно проверить на
живом контроллере: включи в CODESYS-проекте OPC UA Server и пометь
переменные, которые нужно связать с тренажёром, флагом `export`.

## Windows-приложение (Electron)

```bash
npm run electron:dev    # окно Electron поверх dev-сервера, для разработки
npm run dist:win         # тренажёр + помощник → release/*.exe (установщик NSIS)
```

`electron/main.js` — минимальный main-процесс: в dev грузит
`VITE_DEV_SERVER_URL`, в проде — `dist-electron/index.html` через
`loadFile`. `vite.config.ts` в режиме `electron` собирает в
`dist-electron/` с относительными путями (`base: './'`) и без
PWA-плагина (service worker бесполезен под `file://` и не нужен —
офлайн и так гарантирован установкой). Конфигурация электрон-билдера —
в `package.json` → `"build"`: `nsis`-таргет, диалог выбора папки
установки, ярлыки на рабочем столе и в меню Пуск. Иконка — временно
`build/icon.ico` (тот же файл, что у автономного лаунчера тренажёра),
дизайн иконки приложения — отдельная задача на будущее.

**Сборка `.exe` на Linux требует `wine`** (NSIS-тулчейн под Windows
кросс-компилируется через wine) — `apt-get install wine wine32:i386`
(нужен и 32-битный компонент для патча ресурсов у финального exe).
Собирать на самой Windows или в CI `windows-latest` — без `wine`,
`electron-builder` там работает нативно. Именно так настроен CI:
`.github/workflows/build-windows.yml` собирает установщик на
`windows-latest` при пуше в эту ветку и кладёт готовый `.exe` в
артефакты запуска (вкладка Actions → нужный run → Artifacts) — так файл
не упирается в лимиты передачи через чат.

## Телефонная версия (PWA mini)

`npm run build:phone` собирает `dist-phone/` с манифестом «ПЛК Помощник
Mini» и только тремя вкладками (Журнал, Калькуляторы, Справочник) —
тренажёр и модули, рассчитанные на полноценный ввод данных на объекте
(I/O, замечания, паспорт, версии, мастер), в неё не попадают, включая
из офлайн-кэша (`workbox.globIgnores` исключает `trainer/**` в этом
режиме). Раздай `dist-phone/` по HTTPS (например GitHub Pages/Netlify) —
на iPhone открой в Safari и выбери «Добавить на экран Домой», получится
свой значок и офлайн-работа без App Store (настоящее нативное iOS-
приложение из этой песочницы не собрать — нет Mac/Xcode/Apple Developer
account).

## Стек

Vite + React + TypeScript + Tailwind CSS, Dexie.js (IndexedDB),
react-router-dom (HashRouter — работает и под `file://` в Electron),
fuse.js (поиск), papaparse (CSV), jsPDF (PDF), vite-plugin-pwa
(офлайн-кэш для сайта/PWA), Electron + electron-builder (Windows `.exe`),
node-opcua-client (связь с CODESYS, только в main-процессе Electron).

## Разработка

```bash
npm install
npm run dev            # локальный сервер с горячей перезагрузкой
npm run build           # продакшн-сборка (сайт/PWA) в dist/
npm run build:phone      # телефонная PWA в dist-phone/
npm run electron:dev      # окно Electron для разработки
npm run dist:win           # установщик Windows в release/
npx tsc --noEmit             # проверка типов
```

## Справочник (модуль 7)

Исходники пяти томов лежат в `tomes/*.html` (не редактируются руками —
это те же файлы, из которых собираются PDF-книги отдельным инструментом).
Скрипт разбирает их в JSON:

```bash
node scripts/build-reference.mjs
```

Результат — `src/reference-data/*.json`, коммитится в репозиторий (не
генерируется на лету в браузере). Перезапускай скрипт и коммить заново,
если тома обновятся.

## Калькуляторы (модуль 4)

Вся числовая логика — чистые функции в
`src/modules/calculators/formulas.ts`, без React/DOM. Проверяются
отдельным скриптом на известных примерах до того, как попадают в UI:

```bash
node --experimental-strip-types scripts/verify-formulas.mjs
```

При изменении формул — сначала правь и гоняй этот скрипт, потом
переноси в компонент.

## Объекты (линия → шкаф → устройство)

`src/modules/objects/` — общее дерево объектов (`db.objects`,
самоссылающийся `parentId`), переиспользуется модулями 3/5/6 через
`useObjectTree` (плоский список с отступами для выпадающих списков) и
`ObjectPicker` (выбрать существующий объект или создать новый прямо в
форме, без ухода на отдельный экран).

## Замечания (модуль 3)

`src/modules/punchlist/` — список пунктов с приоритетом (A/B/C), статусом
и привязкой к объекту. Открытые пункты приоритета A показывают счётчик
и баннер в самом модуле и красный бейдж в навигации на вкладке
«Замечания» — это единственное предупреждение, которое видно из любого
места приложения.

## Паспорт оборудования (модуль 5)

`src/modules/equipment/` — карточки устройств (CPU, станция I/O,
частотник, панель, коммутатор, …) с серийным номером, прошивкой,
PROFINET/PROFIBUS-адресацией и местом бэкапа; боковой список объектов для
фильтрации, поиск по артикулу/имени, кнопка «Скопировать конфигурацию
похожего устройства» для быстрого заполнения повторяющегося железа,
экспорт в PDF.

## Реестр версий проектов (модуль 6)

`src/modules/versions/` — история версий проекта по объектам (версия,
среда разработки, что изменено, кто изменил, где архив, отметка «сейчас в
контроллере») и отдельная вкладка «Проверка перед выездом на объект»
(`PreDepartureCheck.tsx`): сравнивает сохранённую локально версию твоей
среды разработки (`localStorage['pfa-my-env']`) с последней
зафиксированной версией на объекте и предупреждает при несовпадении, а
также если последняя запись о бэкапе старше 30 дней.

## Мастер диагностики (модуль 8)

`src/modules/wizard/` — пошаговое дерево решений (`wizardData.ts`, чисто
данные — вопросы/варианты/выводы, без логики в компоненте) по пяти
типовым веткам из ТЗ: станция сети недоступна, один вход не работает,
CPU в STOP, всё встало без сообщений, работает через раз. На каждом шаге
на экране висит напоминание проверить Force. В конце ветки — кнопка
«Сохранить случай в журнал», создающая запись в `db.faultLogs` с
предзаполненными симптомом/причиной/устранением из вывода мастера.

## Статистика

`src/modules/statistics/StatisticsPage.tsx` — сводка по всем таблицам:
суммарный простой и топ объектов/тегов по журналу неисправностей,
статусы точек I/O, открытые/закрытые замечания по приоритетам,
оборудование по типам. Никакого отдельного хранилища — просто агрегация
существующих таблиц через `useLiveQuery` при каждом открытии вкладки.

## Структура

```
src/
  db/schema.ts          # Dexie: таблицы и версии (v2: + punchList, equipment, projectVersions)
  lib/                    # search.ts (Fuse), csv.ts, pdf.ts — общие утилиты
  modules/
    trainer/                # вкладка «Тренажёр» — iframe на public/trainer/index.html
    codesys/                  # панель связи с CODESYS по OPC UA (только Electron)
    calculators/                # модуль 4
    faultlog/                   # модуль 1
    io-table/                     # модуль 2
    objects/                        # дерево объектов, общее для 3/5/6
    punchlist/                        # модуль 3
    equipment/                          # модуль 5
    versions/                             # модуль 6
    wizard/                                 # модуль 8
    statistics/                               # статистика
    reference/                                  # модуль 7
  reference-data/                                # сгенерированный JSON из tomes/
scripts/
  build-reference.mjs                             # tomes/*.html -> reference-data/*.json
  verify-formulas.mjs                               # проверка калькуляторов
tomes/                                                # исходные HTML-тома + style_v2.css
public/trainer/                                         # копия корневого index.html (тренажёр)
electron/
  main.js                                                 # Electron main-процесс (+ IPC-ручки codesys:*)
  preload.cjs                                               # contextBridge -> window.electronAPI.codesys
  opcuaBridge.js                                              # обёртка над node-opcua-client
build/icon.ico                                              # временная иконка Windows-приложения
```
